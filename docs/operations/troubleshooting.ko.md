# 문제 해결

`containerctl doctor`로 시작한다. 머신 설정을 보고하고 아무것도 바꾸지 않는다.
`containerctl status`는 무엇이 실행 중인지 보고한다.

| 증상 | 원인 | 조치 |
| --- | --- | --- |
| 이름이 해석되지 않는다 | DNS 에이전트가 등록되지 않았다 | `containerctl install` |
| 에이전트가 등록됐는데도 해석되지 않는다 | 프록시가 없는 동안의 응답이 캐시됐다 | 몇 초 뒤 다시 시도 |
| 프록시가 502를 반환한다 | 컨테이너는 실행 중이나 해석된 포트를 듣지 않는다 | `containerctl logs <서비스>` 후 `containerctl schema`의 포트 순서 확인 |
| 프록시가 404를 반환한다 | 그 이름을 가진 라우트가 없다. 서비스가 정지했거나 internal이거나 도메인이 다르다 | `containerctl status` |
| 라우트가 있는 이름에 인증서 경고 | 인증 기관이 신뢰되지 않았다 | `containerctl install` |
| 라우트가 없는 이름에 인증서 경고 | 상위가 라벨 하나인 와일드카드는 클라이언트가 거부한다 | `shop.test`처럼 라벨 두 개인 도메인 사용 |
| 명령이 암호를 묻는다 | 프로젝트가 아직 위임되지 않은 도메인을 쓴다 | 정상. 도메인마다 한 번 묻는다 |
| 고친 뒤에도 브라우저만 실패한다 | 브라우저가 인증서를 캐시했다 | 새 창을 연다 |
| 이름이 시간 초과되거나 504를 반환한다 | 라우트가 재생성 전 컨테이너 주소를 갖고 있다 | `containerctl sync` |

## 어느 대상이 응답했는지

모든 응답에 `X-Containerctl-Route`가 붙는다. `address`는 설정을 만든 그 주소로
컨테이너에 닿았다는 뜻이고, `name`은 그 주소가 응답을 멈춰 컨테이너 이름으로
되돌아갔다는 뜻이다. 이름은 런타임이 해석한다.

```sh
curl -sD- -o /dev/null https://web.test/ | grep -i x-containerctl-route
```

계속 이름으로 응답하는 라우트는 주소가 낡은 것이다. containerctl이 아닌 것이
컨테이너를 재생성했을 때 그렇게 된다. `containerctl sync`가 실행 중인
컨테이너에서 설정을 다시 쓰고 프록시를 리로드한다. 컨테이너는 시작하지도
정지시키지도 변경하지도 않는다.

## 다른 프로그램에서 상태 읽기

```sh
containerctl status --json
```

머신 상태, 등록된 모든 프로젝트, 서비스별 상태와 주소, 인증서 목록을 담는다.

## 프록시가 없을 때

프록시는 라우트를 만드는 명령이 생성하고, 마지막 라우트가 회수되면 제거된다.
아무 프로젝트에서 `containerctl up`을 실행하면 다시 생성된다.
