# 서비스 생명주기

[English](service-lifecycle.md) · [Compose 키](compose-schema.md)

관리 볼륨 생성과 데이터 보존 규칙은 [Named volume](volumes.ko.md)에 있다.

Compose 생명주기 지원은 소스에 구현됐다. 로컬 검증과 설치 바이너리는 기능 표에서 분리해 기록한다.

Compose 디렉터리의 `.env`를 읽으며 프로세스 환경이 우선한다. `${NAME:?message}`, 기본값, 대체값, `$$`를 포함한 치환은 YAML 값에 적용한다. 필수 값이 없으면 해석된 값을 출력하지 않고 거부한다. 상대 bind 원본은 호출 디렉터리와 무관하게 Compose 파일을 기준으로 해석한다. Named volume은 선언이 필요하며 external 이름은 이미 존재해야 한다. 프로젝트 생명주기 명령은 이 볼륨을 제거하지 않는다.

`user`, `read_only`, `cap_drop`는 컨테이너 런타임 옵션으로 전달한다. `depends_on`, `healthcheck`, 볼륨 선언 내부의 미지원 필드는 거부한다. 변경 전에 의존성을 검증한다. 참조는 존재해야 하고 순환은 금지하며 `service_healthy`에는 healthcheck가 필요하다. 짧은 의존성 문법은 `service_started`를 뜻한다.

서비스는 의존성 순서대로 시작한다. `service_healthy`는 선언한 `CMD` 또는 `CMD-SHELL` 검사를 제한 시간·재시도·선택적 시작 유예 시간으로 실행한다. 이는 시작 조건이며 지속적인 백그라운드 상태 감시는 아니다. `service_completed_successfully`로 요구되는 서비스는 제한 시간 안에 내부 일회성 프로세스로 실행한다. 실제 종료값이 0이어야 의존 서비스를 시작한다. 런타임은 중지한 컨테이너의 종료 코드를 제공하지 않으므로 도구는 foreground 실행 성공을 컨테이너 생성·시작 시각 및 해석한 설정·이미지 digest와 함께 기록한다. 일치하는 성공 증거가 없는 중지 컨테이너는 초기화 완료가 아니다.

생명주기 변경 전에 선택한 모든 이름을 검사한다. 컨테이너는 이 프로젝트의 group·service·service-role label을 가져야 하며 다른 프로젝트 또는 소유 정보가 없는 컨테이너는 거부한다. `up`은 변경 없는 실행 중 서비스와 완료가 입증된 초기화를 재사용한다. 설정이나 로컬에서 해석한 이미지 digest가 바뀌면 소유한 해당 서비스만 교체한다. 비교 전에 이미지 참조를 해석하며 로컬 이미지가 있으면 mutable tag의 원격 변경을 확인하지 않는다. 로컬 tag에 같은 name@digest 별칭이 없을 수 있으므로 생성에는 선언한 참조를 사용한다. 프로세스를 시작하기 전에 생성된 컨테이너의 소유자·설정 label·실제 이미지 digest가 해석한 선택과 일치하는지 확인한다. tag가 바뀌어도 검증되지 않은 이미지는 시작할 수 없다. 초기화는 attach한 start를 사용하므로 실제 exit 0만 완료를 허용한다. 명시적인 restart는 재시작 요청으로 유지한다. Bind 파일 내용 변경은 서비스 digest를 바꾸지 않는다. 시작 시에만 파일을 읽는 서비스는 호출자가 명시적으로 재시작해야 한다.

프로젝트 변경은 볼륨을 제거하지 않는다. 의존성 실패는 진행을 중단하며 전체 프로젝트 시작 성공을 반환하지 않는다. 이미 완료한 단계는 원인 조사와 다음 재시도를 위해 확인 가능한 상태로 남긴다. 초기화 fingerprint는 직접 의존성의 현재 설정·이미지·컨테이너 생성 정보를 포함한다. DB 컨테이너를 교체하면 초기화 자체 명령이 같아도 실제 초기화를 다시 실행해야 한다. 볼륨 내용을 직접 변경한 경우는 이 식별 정보로 감지하지 않으며 프로젝트 생명주기 명령은 볼륨을 보존한다.

설정 label 도입 전에 만든 소유 컨테이너를 조용히 교체하지 않는다. 이전 서비스 설정을 입증할 수 없으므로 `up`은 명시적인 restart를 요구한다. 다른 프로젝트는 그대로 둔다.

`.env`는 줄마다 `NAME=value` 하나와 선택적 `export`, 주석, 작은따옴표 literal, 큰따옴표 escape 값을 지원한다. 여러 줄 값은 지원하지 않는다. 빈 값을 포함해 shell 값이 우선한다. YAML mapping 키는 치환하지 않는다. `depends_on` 긴 문법은 `condition`만 지원하며 `restart`·`required` 옵션은 거부한다. Health 시간은 각각 최대 10분, 재시도는 1–100회, 전체 시작 예산은 최대 30분이다. 일회성 명령 제한은 10분이며 시간 초과 시 소유한 해당 컨테이너만 중지하려고 시도한다. 도구가 실행하는 같은 프로젝트 변경은 advisory 파일 잠금을 공유한다.

성공 기록은 `~/.containerctl/completions`의 비공개 파일, 프로젝트 잠금은 `~/.containerctl/locks`에 둔다. 기록에는 명령 출력·환경·비밀을 넣지 않는다. 기록이 없거나 잘못됐거나 컨테이너·시작 시각이 바뀌면 실제 서비스 이름을 사용한 `containerctl restart initialize`가 필요하다. Apple Container 1.3.1은 생성·시작 시각을 초 단위로 제공하며 opaque incarnation ID는 없다. 증거는 이 런타임 식별 정보에 의존한다. 같은 초 안의 여러 외부 재시작을 포함해 같은 로컬 런타임을 조작하는 운영자에 대한 보안 경계는 아니다.

`CONTAINERCTL_SERVICE_E2E=1 go test ./internal/stack -run '^TestServiceLifecycleActualRuntime$' -count=1 -timeout=120s`는 프로젝트 등록·DNS·프록시 변경 없이 고유한 이름의 서비스 컨테이너 3개를 생성한다. 실제 UID/GID, 읽기 전용 root, 빈 capability, 0600 bind 파일, health 순서, 변경 없는 재사용, 초기화 exit 7, 외부 재시작 거부, 모든 기존 컨테이너 보존을 검사한다. 애플리케이션 DB를 검사하거나 배포를 뜻하지 않는다. 일반 `make check`는 컨테이너 실행 없이 parser·의존성·실패·소유권·완료 증거를 검사한다.

TCP 준비 상태 보고는 선언된 시작 조건과 별개로 유지한다. 경로 동기화 후 `up`·`start`·`restart`는 선택한 장기 실행 서비스가 연결을 받을 때까지 기다리고 느린 서비스를 시작 중으로 보고한다. 완료된 일회성 서비스는 이 대기에서 제외한다. 대기 대상이 없으면 준비 상태를 조회하거나 연결 성공 메시지를 출력하지 않는다. 선언한 healthcheck나 초기화 실패는 여전히 시작 실패로 처리한다.

프로젝트는 그 프로젝트를 위한 어떤 일보다 먼저 등록한다. 등록이 그 프로젝트를 이 기계의 것으로 만드는 행위이고 창은 등록부를 그리므로, 먼저 등록된 프로젝트는 이미지를 받고 컨테이너를 만드는 동안 화면에 있고 실행이 실패해도 그대로 있다. 성공에 대한 보상처럼 일이 끝난 뒤에 등록하면, 몇 분 걸리는 실행은 그동안 보이지 않고 실패한 실행은 끝내 보이지 않는다.

잠깐을 넘길 수 있는 모든 단계는 시작하기 전에 서비스와 단계를 말한다. 이미지 받기, 컨테이너 만들기, healthcheck 기다리기가 그것이다. 그러면 어느 단계에서 멈춘 명령인지 이미 출력된 것만으로 읽을 수 있다. 끝난 뒤에 보고하는 것은 명령이 어디에 걸렸는지 아무에게도 알려주지 않는다.

실패는 실패한 서비스의 출력을 함께 보고한다. 멈추거나 0이 아닌 값으로 끝나거나 끝내 건강해지지 않은 서비스는 그 이유를 자기 로그에 남기고 끝난다. 이유 없이 단계 이름만 말하는 명령은 운영자에게 손댈 것을 남기지 않는다. 크래시한 데이터베이스를 healthcheck 중 멈췄다고만 보고하면, 컨테이너 로그에 그대로 있는 크래시가 가려진다. 그 로그의 마지막 줄들을 오류와 함께 출력한다.

생성 실패는 런타임이 한 말을 보고한다. 런타임은 무엇 때문에 거부했는지를 지목한다. 없는 경로, 이미 쓰인 이름 같은 것이다. 분류만으로는 아무것도 지목하지 못한다. 없는 bind 원본을 생성 거부라고만 보고하면 읽는 사람에게 만들어야 할 경로가 남지 않는다. 분류는 유지하고 그 뒤에 런타임의 문장을 출력한다.

그 문장에서 하나는 가린다. 환경 값은 명령줄로 전달되므로 인자를 되울리는 런타임은 값도 함께 되울린다. 이 명령이 전달한 모든 `KEY=VALUE`를 `KEY=`와 자리표로 바꾼 뒤에 문장을 출력한다. 추측이 아니라 정확하다. 키와 값은 이 도구가 방금 넘긴 것들이다. 값은 자기가 실려 온 인자의 일부로만 되울려지므로, 쌍을 가리면 짧은 값처럼 읽히는 평범한 단어를 건드리지 않고 덮인다.

출력을 감추는 것은 아무것도 지키지 못했다. 같은 사람이 같은 터미널에서 `containerctl logs` 한 번이면 같은 바이트를 보므로, 그 규칙은 비밀을 사지 못하고 필요한 순간의 증거만 잃었다. 대신 지키는 것은 출력이 가는 곳이다. 명령 자신의 오류 스트림에만 쓰고 그 밖에는 쓰지 않는다. 머신 상태에도, 완료 기록에도, 이 도구가 남기는 어떤 파일에도 복사하지 않으며 명령보다 오래 남지 않는다. 마지막 `FailureLogLines`줄로 제한한다.

로그 저장을 금지한 값은 프로그램이 출력하지 않아야 한다. 이 도구는 애플리케이션별 값을 필터링하지 않으며, 자기 로그에 비밀을 출력하는 서비스는 여기에도 출력한다.

도구가 attach 출력을 버려도 네이티브 런타임은 초기화 stdout을 로그에 보존한다. `TestLocalImageTagActualRuntime`이 고정된 공개 marker로 이를 검증한다. 로그 저장을 금지한 값은 프로그램이 출력하지 않아야 하며 containerctl은 애플리케이션별 값을 필터링하지 않는다.
