# Service lifecycle

[한국어](service-lifecycle.ko.md) · [Compose keys](compose-schema.md)

Managed volume creation and data-preservation rules are in [Named volumes](volumes.md).

Compose lifecycle support is implemented in source. Local verification and installed binaries are recorded separately in the feature table.

The Compose directory supplies `.env`; the process environment takes precedence. Interpolation applies to YAML values, including `${NAME:?message}`, defaults, alternatives and `$$`. Missing required values are rejected without printing resolved values. Relative bind sources are resolved against the Compose file, regardless of the caller's directory. Named volumes must be declared; external names must already exist and are never removed by project lifecycle commands.

`user`, `read_only` and `cap_drop` become container runtime options. Unsupported fields inside `depends_on`, `healthcheck` and volume declarations are rejected. Dependencies are validated before changes: references must exist, cycles are forbidden, and `service_healthy` requires a healthcheck. Short dependency syntax means `service_started`.

Services start in dependency order. `service_healthy` runs the declared `CMD` or `CMD-SHELL` check with a timeout, retries and optional start period. This is a startup gate, not continuous background health monitoring. Progress lines report each started container, the health budget the gate may use, each failed attempt with its elapsed time and attempt count, and the elapsed time at which the service became healthy, so a start period of minutes is never a silent wait. A service required as `service_completed_successfully` runs as an internal one-shot process with a bounded deadline. Its actual exit must be zero before dependants start. The runtime does not report stopped containers' exit codes, so the tool records a successful foreground exit against the container's creation/start timestamps and resolved configuration/image digest. A stopped container without matching success evidence is not a completed initialization.

Every selected name is checked before lifecycle changes. A container must carry this project's group, service and service-role labels; another project's or unowned container is refused. `up` reuses an unchanged running service and a proven completed initializer. Configuration or locally resolved image digest changes replace only the owned service. Image references are resolved before comparison; mutable tags are not polled against registries when a local image exists. Creation uses the declared reference because local tags need not have an equivalent name@digest alias. Before starting the process, the tool verifies the created container's owner, configuration label and actual image digest against the resolved selection. A changed tag cannot start an unverified image. Initializers use attached start so only their actual exit zero permits completion. The attached start can return before the runtime reports the container stopped, so the tool reads the container every 100 milliseconds, as it does while waiting for a service to run, until the runtime reports it stopped or the one-shot deadline ends. It then compares the container's state, creation time, start time, configuration label and image digest with the container it started; the error names each field that differs. Explicit restart remains a restart request. Bind-file content changes do not change the service digest; callers must explicitly restart a service that reads changed files only at startup.

Before replacing an owned running service, the command stops it through the runtime and removes it without force. A failed stop returns its error and prevents removal or creation. A stopped service requires no additional stop.

Project changes never remove volumes. Failed dependencies stop progression without claiming that the whole project started. Already completed steps remain inspectable for diagnosis and a later retry. Initializer fingerprints include direct dependencies' current configuration, image and container creation identity: a replaced database container requires another real initialization even when the initializer's own command is unchanged. Changes made directly to volume contents are not detected by this identity; project lifecycle commands preserve volumes.

An owned container created before configuration labels existed is not silently replaced: `up` requires an explicit restart because its previous service configuration cannot be proven. Other projects remain untouched.

`.env` accepts one `NAME=value` per line, optional `export`, comments, single-quoted literals and double-quoted escaped values. Multiline values are unsupported. Shell values win, including empty values. YAML mapping keys are not interpolated. `depends_on` long syntax supports `condition` only; `restart` and `required` options are rejected. Health durations are at most ten minutes each, retries are 1–100, and the total startup budget is at most thirty minutes. A one-shot command has a ten-minute deadline; timeout attempts to stop only its owned container. Every project's tool-driven mutations share an advisory file lock.

Successful completion records are private files under `~/.containerctl/completions`; project locks are under `~/.containerctl/locks`. Records contain no command output, environment or secrets. Missing, malformed, changed-container or changed-start records require `containerctl restart initialize` (using the actual service name). Apple Container 1.3.1 exposes creation/start timestamps at second precision and no opaque incarnation ID. The proof relies on those runtime identities; it is not a security boundary against an operator manipulating the same local runtime, including multiple external restarts within one second.

`CONTAINERCTL_SERVICE_E2E=1 go test ./internal/stack -run '^TestServiceLifecycleActualRuntime$' -count=1 -timeout=120s` creates three uniquely named service containers without project registration, DNS or proxy changes. It checks effective UID/GID, read-only root, empty capabilities, a 0600 bind file, health ordering, unchanged reuse, initializer exit 7, external restart refusal and preservation of every preexisting container. It does not exercise an application database or represent a deployment. The normal `make check` covers parser, dependency, failure, ownership and completion evidence tests without starting containers.

Before route synchronization gives a running proxy the route of a started long-running service, `up`, `start` and `restart` wait until the proxy container itself opens a connection to the service's address, as described in [the architecture](architecture.md#configuration-reload), and fail when it does not within 60 seconds. TCP readiness reporting remains separate from declared startup conditions. After route synchronization, `up`, `start` and `restart` wait for the selected long-running services to accept connections and report slow services as starting. Completed one-shot services are excluded from that wait. An empty wait set performs no readiness lookup and prints no connection-success message. A failed declared healthcheck or initializer still fails startup.

A service's port is the one its Compose file declares: the `containerctl.port` label, then `expose`, then the container side of `ports`. A service that declares none has no port. It is not checked for connections, and it is running when its container runs. A service with a domain needs a port for the proxy to forward to, and one that declares none is refused when the file is read, naming the service and the domain. A port of 80 was assumed when none was declared: a container running `sleep infinity` was then checked on port 80, never accepted a connection, and was reported as not working on a port it never declared.

No port is written anywhere for a service without one: the window has no port row for it, its address has no port, and `containerctl status --json` has no `port` field. Its absence was written as `0` at first, on the service's screen beside the words "read from the Compose file", in its address as `:0`, and in the JSON as `"port": 0`, and `0` is not a port.

A service's state is its container's state as the engine reports it: running, stopped, or absent when there is no container. Whether its declared port accepts connections is a second measurement, recorded beside the state, and only for a running container with a declared port. The two were merged into a state named `starting` with the note "not accepting connections yet", which presented a process its own supervisor had stopped as one about to come up: the measurement says the port did not accept a connection, and nothing about why or whether it will. A port that does not accept connections is reported with its number.

Whether a running service accepts connections is checked on the port its file declares now, not on the port recorded on its container when it was created, since that record can hold a port that was assumed rather than declared.

Stopping and removing are read from the containers, not from the Compose file. The file states what to start; what to stop is what runs under the project's label, `containerctl.group`. A project whose file has been moved, deleted or broken still stops, and so does a service that was removed from the file after it started: its container still carries the project's label, and a `down` driven by the file left it running. The window's Stop failed with `stat …/compose.yaml: no such file or directory` while the project's container was running.

Containers are stopped in the reverse of the order they started, read from each container's start time. Services start in dependency order, so the reverse start order stops a service before the services it depends on without reading the file. Containers that started in the same second are stopped in no defined order between themselves; the runtime reports start times to the second.

A project's command-line name comes from its file when the file is readable, and otherwise from the registry entry recorded for that file's path.

A project is registered before any work is done for it. Registration is what makes the project this machine's, and the window draws from the registry, so a project registered first is on the screen while its images are pulled and its containers are created, and it is still there when the run fails. Registering after the work, as a reward for succeeding, left a run that took minutes invisible and a run that failed invisible for good.

Every step that can take more than a moment says so before it begins, naming the service and the step: pulling an image, creating a container, waiting for a healthcheck. A command stopped in one of them is then readable from what it has already printed. Reporting the steps after they finish tells nobody where a command is stuck.

A failure reports the failing service's own output. A service that stops, exits non-zero or never becomes healthy took its reason with it into its log, and a command that names the stage without that reason leaves the operator with nothing to act on: a crashed database reported only as stopped during its healthcheck hides the crash that is sitting in the container's log. The last lines of that log are printed with the error. A log that cannot be read is reported as unreadable, with the reason the engine gave, and a log with no lines is reported as empty. Neither is left out, because a failure with no word about its log cannot be told from one whose log was never read.

A creation failure reports what the runtime said. The runtime names the thing it refused over — a path that is not there, a name already taken — and a category on its own names nothing: a missing bind source reported as a rejected creation leaves the reader with no path to create. The category is kept and the runtime's sentence is printed after it.

One thing in that sentence is held back. Environment values are passed on the command line, so a runtime that echoes an argument echoes a value with it. Every `KEY=VALUE` this command passed is replaced by `KEY=` and a placeholder before the sentence is printed, which is exact rather than a guess: the keys and values are the ones this tool just supplied. A value is only ever echoed as part of the argument it came from, so redacting the pair covers it without touching ordinary words that happen to read like a short value.

Withholding the output protected nothing. The same bytes are one `containerctl logs` away for the same person at the same terminal, so the rule bought no confidentiality and cost the evidence at the moment it was needed. What is protected instead is where the output goes: it is written to the command's own error stream and nowhere else. It is not copied into the machine state, the completion records or any file this tool keeps, and it does not outlive the command. It is bounded to the last `FailureLogLines` lines.

A program must not print values whose policy forbids logging. This tool does not filter application-specific values, and a service that prints a secret to its own log prints it here too.

The native runtime retains initializer stdout in its logs even when the tool discards attached output. `TestLocalImageTagActualRuntime` verifies this with a fixed public marker. A program must not print values whose policy forbids logging; The tool does not filter application-specific values.

On Apple Container, `up`, `start` and `restart` also require each started long-running service hostname, before starting its dependants, to resolve to exactly the IPv4 and IPv6 addresses declared by its running container before returning success. Address additions and removals are received through macOS DNSServiceGetAddrInfo events. Readiness subscribes once, waits for the exact address set within a 60-second deadline and cancels and collects subscription cleanup on readiness, error or deadline. A request is never retried by this check. Docker network names are private to their network and are outside this host resolver check.

Native address subscriptions use the SDK callback and socket readiness. No repeated address lookup or timer drives the subscription. Closing a subscription cancels its socket wait and collects the worker before returning. CLI build prerequisites include its Go sources and native C headers and sources.
