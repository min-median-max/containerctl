# 피어

상태: 구현되지 않음. 이 문서는 설계를 서술한다. 아래 내용은 아직 바이너리에 없다.

한 네트워크의 두 기계가 각각 containerctl을 실행하며 서로의 도메인에 닿는다.
어느 쪽의 네트워크 설정도 바뀌지 않는다. 공유기 설정도, 네트워크의 DNS 서버도,
hosts 파일도, 특권 포트도 필요 없다.

두 기계 모두 이미 `.test`를 스스로 답하기 때문에 가능하다. 각 기계의
`/etc/resolver/test`가 그 이름들을 자기 `containerdns`로 보내므로, 상대 기계의
이름도 이 프로젝트가 이미 가진 소프트웨어가 답한다.

## 신원

피어는 인증기관의 지문으로 식별한다. 지문이 피어를 저장하는 키이고, 승인의
대상이며, 프록시가 받아들이는 기준이다.

기계 이름과 주소는 피어에게서 읽어오는 속성이다. 바뀌어도 다른 피어가 되지 않고,
비교하지 않으며, 도메인에 넣지 않는다. 이름은 보여줄 뿐 무엇도 결정하지 않는다.

## 기계가 공개하는 것

프록시는 이미 평문 HTTP로 `/__containerctl/health`를 제공한다. 그 옆에
`/__containerctl/peer`가 상대 기계에 필요한 것을 반환한다.

| 항목 | 뜻 |
| --- | --- |
| `name` | 기계의 `LocalHostName`. 표시용 |
| `address` | 네트워크에서 이 기계에 닿는 주소 |
| `domains` | 이 기계가 제공하는 도메인 |
| `ca` | 이 기계의 인증기관. PEM |

## 피어 승인

한쪽 기계에 상대의 주소를 알려준다. `/__containerctl/peer`를 읽어 이름과 도메인,
인증기관의 지문을 보여준다. 승인하면 셋이 일어난다. 피어를 지문으로 저장하고,
인증기관을 사용자 신뢰 설정에 추가하고, 그 주소를 프록시가 받아들인다.

인증기관을 사용자 신뢰 설정에 추가하는 데는 관리자 권한이 필요 없다. 이 기계
자신의 인증기관도 그렇게 신뢰되고 있다.

## 도달

프록시가 80번과 443번을 공개한다. 공개에 관리자 권한이 필요 없다. 런타임의
네트워크 헬퍼가 이미 그 권한을 갖고 있다.

승인된 피어의 주소만 받아들인다. 다른 주소에서 온 요청은 어떤 이름을 대든
거부한다.

## 이름 해석

`containerdns`는 다음 순서로 답한다.

1. 이 기계의 컨테이너가 그 이름을 제공한다: 이 기계의 프록시를 답한다.
2. 승인된 피어가 제공한다: 그 피어의 주소를 답한다.
3. 그 외: 지금과 같이 답한다.

1번이 2번보다 앞이므로, 이 기계가 제공하는 이름은 언제나 이 기계의 것이다.

## 도메인 중복

두 기계가 같은 도메인을 제공하게 될 수 있다. 프로젝트를 시작할 때 피어에게 묻지
않기 때문이다. 상대 기계에 닿든 닿지 않든 프로젝트는 시작되어야 한다.

그것을 이유로 무엇도 거부하지 않는다. 위 해석 순서에 따라 각 기계가 자기 것을
제공하고, 창이 그 이름이 여러 곳에서 제공된다고 알린다. 한쪽에서 도메인을 바꾸면
끝난다.

## 하지 않는 것

- 도메인에 기계 이름을 넣지 않는다. `web.<기계>.test` 같은 것은 없다.
- 기계 이름의 유일성을 따지지 않는다. 두 피어가 같은 이름을 가져도 된다.
- 네트워크를 바꾸지 않는다. 공유기, 네트워크의 DNS, 상대 기계의 시스템 설정을
  건드리지 않는다.
- 승인된 피어가 아닌 것에는 접근을 주지 않는다. 주소와 이름을 모두 아는 기계도
  마찬가지다.

## 설계 전에 측정한 것

| 질문 | 답 |
| --- | --- |
| 프록시가 관리자 권한 없이 443번을 잡는가 | 잡는다. `container run -p 443:80`이 `*.443`에 붙었고 기계의 네트워크 주소가 200을 반환했다 |
| 주소만으로 무엇에 닿는가 | 404. 주소와 맞지 않는 기본 인증서가 제시된다 |
| 주소와 올바른 이름으로 무엇에 닿는가 | 그 사이트 |
| 프록시가 받아들이지 않는 주소에서 주소와 올바른 이름으로 무엇에 닿는가 | 403 |
